# Security model

## Identity and authorization

The standalone process authenticates to Frappe with either an API token or the standard login endpoint. Requests execute as that user, and Frappe's resource/method APIs enforce its permissions and validation. API tokens are preferred outside local development.

## Transport

One rule covers both auth modes: `FRAPPE_URL` must use HTTPS unless the host is a loopback address (`localhost`, `127.0.0.1`, `::1`) or ends in `.localhost`. An API token is a long-lived credential sent on every request, so plain HTTP to any other host is refused before any request goes out, for token auth as well as password login.

Development networks sometimes reach the site by a container service name such as `http://frontend:8080`. For those, set `FRAPPE_ALLOW_INSECURE_HTTP=YES` (exactly that value). The server then allows plain HTTP to any host and logs one warning to stderr at startup. Use it only on a network you trust; credentials and data travel unencrypted.

## One site per process

Each server process talks to exactly one site, fixed by `FRAPPE_URL` and `FRAPPE_SITE` at startup; no tool takes a site argument. The login session, the metadata cache, `FRAPPE_APPS_PATH`, and the preview tokens all belong to that site, so a preview from one site can't be confirmed on another. Run one server per site to work with several (FR-2026-002 was closed as won't do).

`FRAPPE_SITE_LABEL` is informational: `get_site_info` returns it so an agent can check which connection it is using, and it is never used to choose a target. It is validated at startup (1–64 characters, `_SAFE_NAME`), so it can't smuggle anything into a message. It is only as trustworthy as the host configuration that sets it.

## Remote targets are read-only by default

A target whose `FRAPPE_URL` host isn't loopback or `.localhost` starts with only the `read` toolset. Writes need `FRAPPE_MCP_READ_ONLY=NO`, an explicit setting the startup log and `mcp-frappe check` both report as a warning. A writable toolset named in `FRAPPE_MCP_TOOLSETS` without it stops the server at startup, so writes are never dropped or enabled silently. Removed tools are not listed and can't be called.

## Setup check

`mcp-frappe check` prints the settings it used without their secrets: the auth mode and username, never the API key, secret, or password, and `FRAPPE_URL` reduced to scheme, host, and port so that credentials embedded in the URL stay out. If an error message from the site or the network echoes a configured secret of eight or more characters, the output shows `***` instead. It does not print the `FRAPPE_APPS_PATH` path, only which site apps have a checkout there and whether each is writable. Its output is meant for the user's terminal; review it before pasting it into an issue.

## Sessions

A failed password login is never cached: the next tool call tries to log in again instead of continuing as Guest.

When a password session expires, Frappe treats requests as Guest and rejects them with HTTP 401 or 403 before running them. On such a response the server asks `/api/method/frappe.auth.get_logged_user` who it is. If that call fails or answers `Guest`, the session has expired: the server logs in again and retries the original request once. If the user is still logged in, the response is a real permission denial and is returned unchanged, with no retry and no other endpoint tried. Token auth never re-logs in, because a token does not expire with a session.

Administrator is a full-privilege account. `FRAPPE_USERNAME` defaults to `Administrator`, but there is no default password: password login needs `FRAPPE_PASSWORD`, and without it the server needs an API key and secret. Prefer a less privileged user where the task allows it, and do not expose a local development site with a default password to a network.

## Human approval

`confirm=true` is not a human checkpoint: the model sets it itself. The preview tokens (`expected_modified`, `preview_id`) guard against stale state, so a change applies only to the record or files the preview showed; they do not stop a model that decides to confirm.

The human checkpoint is the MCP host. Every tool declares MCP annotations: the `read` toolset, `list_allowed_methods`, and `make_mapped_document` have `readOnlyHint: true`, every other tool `readOnlyHint: false`, and tools that delete or can remove data (`delete_document`, `cancel_document`, `delete_doctype`, `update_doctype`, `set_role_permissions`, `rollback_export`, and `call_allowed_method`, whose listed methods can do anything) `destructiveHint: true`. A host can run read tools without asking and ask a person before any write, which is what the annotations are for. Annotations are hints a host chooses to follow; configure the host to require approval for non-read tools.

To take writes away entirely, start the server with `FRAPPE_MCP_READ_ONLY=YES` (or narrow `FRAPPE_MCP_TOOLSETS`; remote targets are read-only unless `FRAPPE_MCP_READ_ONLY=NO`): the unselected tools are removed at startup and never listed. The connected Frappe user's permissions still bound what any remaining tool can do.

Error text returned to the model is decoded from Frappe's messages and never includes the server traceback (`exc`), which can hold file paths and code; it is capped at 2,000 characters. When the site can't be reached, the error names the site as `scheme://host[:port]` and the kind of failure (connection refused, timed out, host name not resolved) without the network library's text, so no URL credentials, path, or query reach the model.

## Tool boundaries

- There is no arbitrary Python, SQL, or unrestricted dotted-method tool. App methods are called only from the user's allowlist ([next section](#allowlisted-method-calls)).
- Lists and report output have explicit caps.
- Document changes preview first; update/delete confirmations require the current `modified` token. Updates also send that token to Frappe, which re-checks it under a row lock (`check_if_latest`), so a change between the check and the write is refused.
- Field names in reads, filters, and writes are checked against the DocType's metadata (Custom Fields and Property Setters included); filter operators are allowlisted, and four-element filters may only name the DocType's own child tables. Writes refuse standard columns and read-only fields.
- Metadata comes from Frappe's form loader (`frappe.desk.form.load.getdoctype`), which Frappe serves to any logged-in user, as it does for Desk. The record tools never read the System Manager-only `DocType`, `Custom Field`, or `Property Setter` resources, so they work for any user with permission on the DocType, and Frappe checks that permission on every record read and write. Metadata is cached for `FRAPPE_META_TTL` seconds (default 300); a schema change made outside the MCP is seen once its entry expires, and Frappe's own validation still applies to every write. Set `FRAPPE_META_TTL=0` to always read fresh metadata.
- Frappe's API validates writes and applies the connected user's roles and permissions.
- The record tools (`create_document`, `update_document`, `delete_document`) keep to record data. Schema and configuration DocTypes are refused with the dedicated tool to use: `DocType`, `DocField`, `DocPerm`, `Custom Field`, `Property Setter`, `Custom DocPerm`, and `Customize Form` go to the schema tools, `Workflow`, `Notification`, `Report`, and `Workspace` to their `upsert_*` tool, so the checks those tools run can't be skipped. `delete_document` still deletes Custom Fields, Property Setters, Custom DocPerms, Workflows, Notifications, Reports, and Workspaces, because no other tool does and a delete writes no code; a DocType delete goes to `delete_doctype`. Records that hold code are refused by all three tools (next section).
- Schema creation uses native `DocType`, `Custom Field`, and `Property Setter` resources and remains subject to server permissions. DocType field types and validation are handled by Frappe's controller.
- `update_doctype` and `delete_doctype` refuse standard DocTypes of `frappe` and `erpnext`. `update_doctype` allowlists DocField properties and DocType settings; it accepts `depends_on`, `mandatory_depends_on`, and `read_only_depends_on` (as `set_field_property` does) but refuses `collapsible_depends_on`, `ignore_xss_filter`, and `options` on HTML and Button fields, which Frappe evaluates or renders as code. It refuses fieldname changes (that is `rename`'s job) and fieldtype changes that can lose data. `delete_doctype` refuses DocTypes that other DocTypes link to. Neither writes local files: Frappe writes or removes a standard DocType's app files itself in developer mode.
- `diff_doctype` and `list_app_drift` are read-only. They read the `DocType`, `Module Def`, `Custom Field`, and `Property Setter` resources (System Manager, as for the other schema tools) and local files only below `FRAPPE_APPS_PATH`.
- `list_pending_patches`, `get_recent_errors`, and `list_app_methods` are read-only. `Patch Log` and `Error Log` are System Manager records, read with the user's permissions. Local files are read only below `FRAPPE_APPS_PATH`: `patches.txt` with the same checks as `diff_doctype`, and the app's `.py` files resolved one by one, a file outside the app skipped. App code is parsed with `ast`, never imported or run, and `execute:` lines in `patches.txt` are returned as text. Error Log tracebacks can contain record values; the tool returns only the last 40 lines (at most 4,000 characters) and its description tells the agent to show the user only what is needed.
- `promote_custom_doctype` refuses `frappe` and `erpnext`, modules of other apps, custom modules, and an existing DocType folder. It changes only the DocType's `custom` flag and `module`, with the preview's `modified`.
- `customize_doctype` calls `run_doc_method`, Frappe's generic document-method endpoint, with two fixed methods only: `fetch_to_customize` (a `GET`, so Frappe keeps no writes) and `save_customization`, on the Customize Form document. Neither the method nor the document type comes from the model, so this isn't the open dispatch `FRAPPE_MCP_METHODS` refuses. Frappe checks read permission on Customize Form (System Manager) and runs the whole Customize Form validation. The operations use the property allowlists of `update_doctype`, intersected with Customize Form's own, and refuse the same code-like properties; values the form already holds are sent back unchanged. The `preview_id` binds the DocType's `modified` and every Property Setter and Custom Field of the DocType.
- `rename` uses Frappe's own rename endpoints (`update_document_title`, Custom Field `rename_fieldname`), which check write permission, Allow Rename, System Manager, and, for a standard DocType, Developer Mode and Administrator. It refuses records that hold code and schema records (a DocType rename has its own kind, limited to the user's apps), and confirms with a `preview_id` that binds `modified`.
- `set_role_permissions` calls Frappe's System Manager-only Permission Manager endpoints; it requires an existing role and DocType.
- `export_form_customizations` previews source record timestamps and app-file destinations, then checks for System Manager and calls Frappe's native exporter. The app/module must belong together on the target site; Frappe's permissions remain authoritative.
- `upsert_workflow` and `upsert_notification` build Workflow and Notification records from a checked shape: roles must exist, states and fields must belong to the DocType, and the fields Frappe evaluates as code are refused (next section). `get_workflow` and `list_notifications` are read-only. Both upserts preview first and need the current `modified` to replace a record.
- `upsert_report` writes only Report Builder reports. Columns, filters, `order_by`, and `group_by` are checked against the DocType's metadata, and `order_by` is rebuilt from fieldnames, so no SQL text reaches the saved `json`. Its post-save sample uses `frappe.desk.reportview.get_list`, which applies the user's permissions, and returns at most 5 rows.
- `upsert_workspace` saves public Workspaces of non-custom modules of apps other than `frappe` and `erpnext`. Every shortcut, link, and number card must point to an existing DocType, Report, Page, or Number Card; `URL` shortcuts are refused. `get_workspace` is read-only.
- Report execution uses Frappe's report API; report permissions still apply. `run_report` drops the `chart` unless asked and pages the rows. `list_reports` reads the `Report` list (Frappe v16 grants read to Desk users) and `get_report_filters` calls `frappe.desk.query_report.get_script`, which checks the report's roles; it returns the Report Filter rows and the report's JavaScript (cut to 8,000 characters), never its HTML print format.
- `list_documents` rebuilds `order_by` from checked fieldnames and `asc`/`desc`, so no SQL text reaches Frappe; `or_filters` gets the same checks as `filters`. Pages are capped at 100 rows (500 for `list_doctypes`).
- `count_documents` uses `frappe.client.get_count`, which counts only records the user may read. `search_records` calls `frappe.desk.search.search_link` with the DocType's own search settings; it never sends a `query` method (which would dispatch to an arbitrary whitelisted function) or `ignore_user_permissions`, and returns at most 50 results.
- `get_site_info` returns the user, app titles and versions (branch and commit details dropped), and which site apps have a checkout under `FRAPPE_APPS_PATH`; it returns no local paths.
- `submit_document` and `cancel_document` need the current `modified`, refuse DocTypes that aren't submittable, and refuse DocTypes with an active Workflow: a direct submit or cancel there would skip the workflow's transitions and roles, because Frappe only moves the document to the first state with the new docstatus.

## Allowlisted method calls

`call_allowed_method` and `make_mapped_document` call whitelisted methods by their dotted path, which AGENTS.md allows only with a per-method allowlist. The allowlist is a JSON file the user writes and names in `FRAPPE_MCP_METHODS`; the server never writes it, and without it the method tools aren't registered. The model can't add an entry: `list_app_methods(as_config=True)` only suggests entries for the user to review.

- **Only listed methods run.** Each tool looks the method up in the loaded file before sending anything and refuses a method that isn't there, or that is listed with another kind. There are no wildcards, and each entry names one dotted path.
- **No dispatchers.** The loader refuses `frappe.client.*` (generic record reads and writes, which would skip the record tools' guards against code DocTypes and fields) and methods that run another method by name (`make_mapped_doc`, `map_docs`, `run_doc_method`, `runserverobj`, `execute_action`). `make_mapped_document` calls `make_mapped_doc` itself, but only with a `mapper` entry's method.
- **Arguments are checked.** `params` fixes the names, types, and allowed values; without it, only scalar values are sent, and only names the function takes when the app source was checked. `cmd` (Frappe's name for the method to run) and `ignore_permissions` are never sent, whatever the entry says.
- **Entries are checked against the source.** With a checkout of the method's app under `FRAPPE_APPS_PATH`, startup fails unless the method is a whitelisted module function whose HTTP methods fit its kind. This catches a typo or a stale entry; it reads the checkout, which can differ from the running code, and doesn't follow `override_whitelisted_methods`.
- **Frappe still decides.** Every call runs as the connected user: Frappe checks that the method is whitelisted and the method checks its own permissions (a mapper checks read access on the source; ERPNext's `get_payment_entry` checks create access on Payment Entry). Mapper and `read` calls are `GET` requests, which Frappe rolls back at the end unless the method commits on its own; `write` calls are `POST` requests and need a preview and `confirm`.
- **Outputs are bounded.** List results are paged, and nested values, strings, and the total size are capped.

**The user is responsible for what they list.** A whitelisted method can do anything its code does, including writes a `read` entry's `GET` won't roll back if the method commits, and some accept arguments that widen what they touch. List only methods you have read, prefer `params` to the scalar default, and list anything that changes data as `write` so it is previewed. A `write` confirmation is the model's own `confirm=true`; rely on the host's approval prompt (`call_allowed_method` has `destructiveHint: true`) for a human checkpoint.

## Bench commands

Until stage 18 the server only sent HTTP requests to the site and wrote files below `FRAPPE_APPS_PATH`. `run_bench` widens that boundary on purpose, with the project owner's approval (2026-11-20): it starts a `bench` process, and Bench runs the app's own code (patches, hooks, tests). AGENTS.md allows it only as this opt-in toolset. The limits:

- **Off by default.** The tool is registered only when the user sets `FRAPPE_BENCH_PATH`, and the model can't set or change that, the site, the command, or the timeout.
- **Local sites only.** With `FRAPPE_BENCH_PATH` set, the server refuses to start unless `FRAPPE_URL` is loopback or `.localhost`, and the tool checks again on every call. Read-only mode leaves the `bench` toolset out.
- **A fixed command list.** `migrate`, `reload-doc`, `export-fixtures`, `clear-cache`, and `run-tests`, each with its own argument rules. The argv is the configured command, `--site <site>`, fixed words, and names that match the safe-name pattern (which can't start with `-`) or, for `test_module`, a dotted path inside the app. There is no flag (`--force`, `--skip-failing`), no free text, and no shell. `bench build`, `install-app`, `get-app`, `backup`, `restore`, `drop-site`, `console`, `execute`, and anything on another site are out of scope.
- **Checked against the site and the checkout.** Apps and modules must exist on the site and belong together; `reload-doc` needs the DocType's file in the checkout, naming that DocType; `export-fixtures` refuses `frappe` and `erpnext`; `run-tests` needs `allow_tests` in the site config when it can be read.
- **Preview and confirm.** The preview shows the exact argv, the site, a warning, and what the command is about to change (drift, pending patches, fixture files). Confirmation needs its `preview_id`, recomputed just before running, so a site that changed in between is refused. `run_bench` has `destructiveHint: true`, so hosts ask a person before it runs.
- **No secrets in the child process.** The environment is an allowlist (`PATH`, `HOME`, locale, temporary folders, Docker host settings, and similar). `FRAPPE_API_KEY`, `FRAPPE_API_SECRET`, `FRAPPE_PASSWORD`, every other `FRAPPE_*` variable, and `CI` are not passed. To check `allow_tests`, the server reads `site_config.json` and `common_site_config.json`, which hold the database password; it keeps only that one flag.
- **Bounded output.** The result has the last 200 lines (at most 20,000 characters) with configured secrets replaced by `***` and the Bench folder by `<bench>`. Tracebacks can still hold record values or other data the app prints.
- **Time limit.** `FRAPPE_BENCH_TIMEOUT` (default 900 s) kills the process; a command inside a container may keep running there.

**What the user takes on.** `migrate` runs every pending patch and re-imports every changed DocType, fixture, and customization file, so it can change or delete data, and it replaces site changes that the files don't hold (the preview's drift shows `site_ahead` and `diverged` DocTypes). `reload-doc` replaces the site's DocType record with the file. `run-tests` runs test code that writes records. Enable the toolset only on a disposable development site whose Bench and app code you trust.

## Code fields and templates

AGENTS.md forbids adding Python evaluation, and a field Frappe evaluates is Python evaluation by another route, so the configuration tools never write one:

- The record tools refuse every DocType whose records hold code Frappe runs (`_CODE_DOCTYPES`, checked against Frappe v16.55.1): Address Template, Assignment Rule, Automation Flow, Client Script, Custom HTML Block, Email Template, Letter Head, Navbar Settings, Print Format, Print Format Field Template, Print Style, Scheduled Job Type (its `method` is a dotted path Frappe calls), Server Script, System Console, Web Form, Web Page, Web Template, Webhook, Website Script, and Website Theme. A denylist can't cover custom apps, so the record tools also refuse a value for any field whose type is `Code`, child-table rows included, in any DocType, using the field type after Custom Fields and Property Setters. A short allowlist (`_PLAIN_CODE_FIELDS`) keeps `Code` fields that hold plain data writable: Translation `source_text` and `translated_text`, ERPNext's `item_tax_rate` JSON on six item tables, and Purchase Order `customer_contact_email`. Auto Repeat `subject` and `message`, which Frappe renders as Jinja though they aren't `Code` fields, are refused too.
- Workflow Transition `condition`, Notification `condition`, and Notification Recipient `condition` are Python expressions Frappe runs with `frappe.safe_eval`. They are refused; Notifications take `filters` instead (`condition_type: Filters`), a JSON filter list Frappe compares as data, validated like `list_documents` filters. A Workflow State's `evaluate_as_expression` (which evaluates `update_value`) is refused too. Conditions set by a person in Desk are not read back as code: `get_workflow` reports only `has_condition`. Replacing a Workflow keeps an existing transition's condition (the preview warns); replacing a Notification clears its conditions (the preview warns).
- Notification `subject` and `message` are Jinja templates Frappe renders on the server with the document and a `frappe` namespace in context. The rule (chosen by the project owner in work-plan stage 08) allows plain text plus `{{ doc.<fieldname> }}` placeholders for fields of the DocType or standard columns, each optionally followed by allowlisted filters with literal arguments: `upper`, `lower`, `title`, `capitalize`, `trim`, `striptags`, `escape`/`e`, `int`, `str`, `flt`, `round`, `truncate`, `default`. Statements, comments, whitespace control, other variables, attribute access beyond the field, indexing, calls, operators, and other filters are refused, so a template can print values of the document and nothing else. `cc` and `bcc` are rendered when they contain `{`, so they must be plain addresses.
- `Custom` and `Method` events (which name a server method) and the Slack and SMS channels are out of scope.
- Query Reports hold SQL (`query`) and Script Reports hold Python (`report_script`, or a module file for a standard one); both are code, so `upsert_report` only writes `report_type: Report Builder`, whose `json` is a list of columns and filters Frappe runs through `frappe.get_list`, and it refuses to replace a report of another type. A Report's `javascript` is never written.
- A Workspace's Custom HTML Blocks hold HTML, CSS, and JavaScript that Desk runs in the browser. `upsert_workspace` has no parameter for them, never sends the `custom_blocks` table, and refuses to replace a Workspace whose layout uses one (or a chart, quick list, or onboarding block it can't rebuild). Workspace link `description` is HTML; the tool never sets it, only carries over what is already there.

## Generated patch files

`rename(kind="field")` is the one tool that writes Python into the app. The project owner approved it in work-plan stage 19 (2026-11-20) under these limits, so it doesn't count as the model writing code:

- The file comes from one constant template (`_RENAME_FIELD_PATCH`) that imports Frappe's `rename_field` and calls `frappe.reload_doc` and `rename_field`. Nothing else can be added.
- Only four values are filled in, each as a Python string literal (`repr`): the DocType name (checked against the safe-name pattern and read from the site), its module folder and DocType folder (scrubbed, and required to be Python identifiers), and the two fieldnames (the old one must exist on the DocType; the new one must be lowercase letters, digits, and underscores, and free).
- The file name and the `patches.txt` line are built from the same checked values. The files are written only below `FRAPPE_APPS_PATH`, inside the app's package, never in `frappe` or `erpnext`, and never over an existing patch file or a line already listed.
- The preview shows every file's diff; confirmation writes them with a backup and a rollback manifest (`rollback_export` restores them), and removes them again if Frappe refuses the DocType save.
- The patch runs only when someone runs `bench migrate` (or the opt-in `run_bench`), with the app's other code.

## Filesystem writes

Filesystem output is optional and local to the MCP process. `FRAPPE_APPS_PATH` is the only writable root; besides app files, the server writes its change journal in `FRAPPE_APPS_PATH/.mcp-frappe-journal/` ([above](#change-journal)). The app and module must exist beneath it, and the selected remote Module Def must belong to that app. Resolved paths are checked against traversal and symlink escapes. Export previews expose paths and content hashes; overwritten files receive a backup before replacement. Exports write only the module's `custom/` folder, the app's `fixtures/client_script.json` (and, with `with_workflows`, `fixtures/workflow.json`, `workflow_state.json`, and `workflow_action_master.json`), and the managed block of `hooks.py`. The configuration tools write no local files; for a standard Notification, Report, or Workspace, Frappe itself writes the module's `notification/`, `report/`, or `workspace/` folder in developer mode. `rename(kind="field")` writes one new patch file, `patches/__init__.py` when it is missing, and `patches.txt` ([above](#generated-patch-files)). `promote_custom_doctype` writes Frappe's controller templates only into a new `<module>/doctype/<doctype>/` folder and removes them again if the DocType is still custom after a failed save. When a standard DocType rename or deletion loses the connection and leaves its app folder in doubt, the server keeps a copy of the original folder (and, for a rename, Frappe's moved folder) under `<app>/.mcp-frappe-backups/doctype-recoveries/<id>/` (mode 0700) and may put the original folder back; it never removes these copies, and the error message gives their local path ([tool reference](tool-reference.md#renames)). The comparison tools only read: DocType JSON and `custom/` files, resolved with the same traversal and symlink checks, each at most 5 MB.

Mount only the intended app tree when running the MCP host in a container. Review exported source and fixtures through Git before migration or deployment. The MCP runs Bench commands only through the opt-in `run_bench` ([above](#bench-commands)); `export-fixtures` writes the app's `fixtures/` files through Bench itself, outside these path checks. It never deploys.

## Change journal

Confirmed writes are recorded in a change journal so they can be listed and undone ([tool reference](tool-reference.md#change-journal-and-undo)). It is `FRAPPE_APPS_PATH/.mcp-frappe-journal/<site label or site>.json`, outside every app's folder, so it isn't committed with an app; the folder gets mode 0700 and the file 0600, a symlinked folder or file is refused, and the file keeps the newest 200 entries. Without `FRAPPE_APPS_PATH` it is kept in memory only.

An entry holds the tool, a timestamp, the names it touched (DocType, record, setter, fieldname, property, app, module, command), and the inverse: names and `modified` values, the `update_doctype` operations of a DocType edit, a Property Setter's old value, and for `update_document` the replaced field values. It never holds credentials, request headers, or the site URL, and a `Password` field's change has no inverse, so no value of one is kept. Writes of business records, whose names and old values can be customer data, are journaled only with `FRAPPE_MCP_JOURNAL_RECORDS=YES`; set it only on a development site with test data, and delete the journal file to forget it. Undo runs the inverse through the same tools as any write, with their checks and Frappe's permissions, after a preview, and only while the target is unchanged since the journaled change.

## Data handling

The MCP host may retain tool inputs and outputs in its own logs. Request only the records and fields needed. Do not put customer data or credentials in public issue reports or evidence. Binary/file browsing and arbitrary whitelisted methods are not exposed by the standalone release.
