# Roadmap: complete Frappe developer pack

## Goal

Deliver a dependable development workflow for Frappe 15 and 16 using this standalone MCP together with Codex or Claude Code and the existing Bench. The MCP remains a bounded HTTP client and local app-file helper; code editing, Git operations, and deployments stay in the coding-agent and owner-controlled environments. Do not add arbitrary Python, shell, SQL, or method dispatch.

## Current baseline

- The MCP already reads and changes records, creates and edits DocTypes, customizes forms, synchronizes supported metadata with app files, manages Workflows, Notifications, Reports, and Workspaces, and exposes opt-in fixed Bench commands including `run-tests`.
- Frappe 15.126 and 16.55 have broad live evidence, including DocType and field matrices. Some later capabilities have only partial v16 evaluation coverage or unit/source evidence.
- The v16.55 live evaluation was historical: mcp-frappe 0.3.0 at `05da805` plus two fixes on 2026-11-21. Current 0.4.0 was subsequently validated against a separately isolated Frappe 16.34 / ERPNext 16.35 stack with its own MariaDB, Redis, Bench, and site. Current-checkout evidence now includes read smoke, nine developer areas, selected Bench commands, role-permission add/update, app diagnostics (22 applied patches, zero pending; 12 DocTypes in sync, one site-ahead), Customize Form label set/revert plus DocType-level Check/Data/Int/Select properties applied and removed, and Custom Field rename/revert. Remaining Phase A gaps are listed below.
- `docs/compatibility-and-validation.md` is the evidence ledger. `docs/work-plan/assessment.md` is historical and must not be treated as a current defect list.

## Phase 0 execution order

1. Run `aspire ps` and `aspire describe frappe` to distinguish resource state from HTTP reachability; never use JSON output that includes environment values unless it is immediately filtered to safe fields.
2. Copy the host-published Frappe desk URL, not a container target port or Socket.IO URL. Probe only `GET /api/method/ping` to verify the route.
3. Run `mcp-frappe check` with the exact environment the MCP host uses. If that passes but a managed MCP connector times out, treat it as a separate host/network configuration issue; `.localhost` is local to the machine running the MCP process.
4. Preserve credentials in the configured secret store/environment. Do not print them, write them to project files, or enable Guest access to work around an authentication error.

## Phase A execution order

1. Run `mcp-frappe check`; identify the exact connected site version and app checkout without printing secrets.
2. Inspect the current Aspire/Bench health and reuse the existing site. Do not create a second site or dependency stack.
3. Use an isolated, uniquely named test DocType/field/role fixture; capture pre-state, preview every mutation, and clean up in `finally`-style steps. Never change business DocTypes or broad production permissions.
4. Validate on v15 first, then v16. At minimum cover the `set_role_permissions` update/add paths, `export_customizations` followed by `run_bench(migrate)` and readback, limited-user permission behavior, and live paths for `customize_doctype`/`rename` and Bench commands not covered by prior evidence. The native Permission Manager has no compare-and-set, so permission writes require a genuinely isolated site/fixture with no concurrent writers; an operator declaration is not a substitute. If that fixture or a safe migration window is unavailable, record the blocker rather than mutating shared configuration.
5. Store sanitized JSON under `e2e/evidence/` and update only the relevant matrix cells. If a major version is unavailable, preserve the gap explicitly rather than infer parity.

## Guardrails and workflow

- Work one phase at a time on a dedicated branch. Do not commit, push, or open a PR unless requested.
- Never use an e2e runner against a shared site unless its setup, unique test names, preview/confirmation, and cleanup have been reviewed first.
- Preserve native Frappe permissions and validation. No SQL, arbitrary Python/shell, or unrestricted dotted method calls.
- For each changed behavior, add focused unit coverage, update tool and agent docs, run the repository's required checks, and retain sanitized evidence only.
- A phase is complete only when its exit criteria are demonstrated; documentation alone does not count as live validation.

## Phase E decision record

The following decisions use the existing Frappe 15.96 source tree and the current official Frappe guide. They are planning evidence, not live acceptance on Frappe 16.

| Candidate | Native source/API evidence | Decision and reason |
|---|---|---|
| Apply a Workflow action | `frappe.model.workflow.apply_workflow` checks that the action is currently a valid transition and checks approval access for the logged-in user before saving. | Defer until a dedicated disposable workflow/DocType fixture can exercise success, denied transition, stale state, and cleanup on both supported majors. Existing shared DocTypes may have active workflows and action side effects. |
| Amend documents | Frappe's amendment linkage and naming are handled in document validation/naming (`amended_from`, cancelled-source validation, amended naming); no generic whitelisted `amend` endpoint was found in the v15 source tree. | Defer; a safe implementation needs per-DocType copy/child-table behavior and a native path proven against v15/v16 controllers. |
| Add/edit comments | `frappe.desk.form.utils.add_comment` checks read permission on the referenced document, then inserts `Comment` with `ignore_permissions=True`; request fields include `comment_by` and `comment_email`. | Defer until the MCP can bind displayed author identity to the authenticated session and verify native Desk-equivalent behavior. |
| Assign/remove users | `frappe.desk.form.assign_to.add/remove` create and cancel ToDo assignments after referenced-document permission checks. | Defer until a disposable record/user fixture is available; assignment changes notify users and create operational ToDos. |
| Upload/download attachments | Frappe uses multipart `upload_file` and a native File record/permission model. | Defer until bounded binary input/output, private-file semantics, size limits, and cleanup can be tested; current record tools intentionally accept JSON only. |
| Render/print PDF | `frappe.utils.print_format.download_pdf` validates print permission and returns a binary PDF response. | Defer until the stdio MCP contract and size limits for binary content are designed and tested across both majors. |
| MCP resources/prompts | These are MCP protocol capabilities; there is no Frappe domain endpoint corresponding to a static prompt/resource. | Defer; the shared Codex/Claude development skill and MCP initialize instructions already provide the agent guidance. Reconsider only for live, site-specific context that cannot be represented safely in that guidance. |
| Built-in Frappe MCP | [Official guide](https://docs.frappe.io/framework/guides-integration/mcp): available from Frappe v16+, Streamable HTTP `/api/v2/mcp`, 13 built-in tools for DocType/method discovery and record CRUD; permission checks remain Frappe's. | Overlaps generic data and method access on v16; does not replace mcp-frappe's local app-file synchronization and fixed Bench tools. v15 has no built-in MCP endpoint. Local live comparison remains unavailable because only the v15 site exists here. |
| `frappectl` | [Official guide](https://docs.frappe.io/framework/guides-integration/mcp) and [upstream README](https://github.com/frappe/frappectl): CLI for REST API v2, Frappe v16+, includes document lifecycle (including amend), files, reports, raw API and SQL query; new profiles default to read-only. | Overlaps generic CRUD/lifecycle/files/reports but not app-aware file export/drift or fixed Bench. Not installed and not live-tested here; do not install or log in against shared v15. Compare on an existing v16 development site before recommending it. |
